Experimental managed Git, nginx and zlib recipes

Status

These factories project valid Build IR and explicit runtime commands. They have
NOT been built or executed with a managed seed. The current catalogue has no
managed compiler/shell/make seed; zlib.srx is a parameterized source factory,
not an admitted binary dependency. bootstrap.srx is only a
copied glibc bootstrap fixture. HostBootstrap still mounts and inventories host
tools; its execution cannot establish managed-build proof. BuildStep::Copy/Move/
Extract run natively. The worker clears the environment and defaults Managed
PATH to empty; recipes must supply tools and lookup paths through declared inputs.
Build.profile is mandatory: these source factories declare Managed; existing
hello/glibc/bootstrap recipes use HostBootstrap. Normal realization now routes
Managed through its dedicated preparation, systemd supervision and publication
path, without falling back to HostBootstrap. It requires explicit [build.managed]
configuration: worker, worker-sha256, scope, socket-parent, and user-bus for user
scope. Worker admission checks pinned static ELF bytes before initializing the
Store. Configuration parsing alone proves neither manager authority nor isolation.
Projection tests and the implemented execution route do not establish a successful
seed -> glibc -> Hello build; that real execution remains pending.
No zero-argument recipe() export is supplied for these factories, so catalogue
publication does not advertise an unavailable toolchain or invent a seed pin.

Use and outputs

managed_glibc(toolchain) is exported from main.srx and produces glibc-managed
dev/out with the existing glibc 2.44 source pin shared in glibc_source.srx.
It consumes the five Toolchain outputs described below. The default glibc recipe remains HostBootstrap.
Its configure receives --with-headers from the sysroot output's usr/include directory;
Configure's CC and BUILD_CC explicitly select compiler/usr/bin/gcc, --sysroot and the bootstrap
loader/RUNPATH so conftest and build-only helpers can run against the seed libc.
Both make invocations override CC on the command line with compiler/usr/bin/gcc + --sysroot
ONLY, and override BUILD_CC separately with the bootstrap command. This prevents
configure's saved CC from injecting the seed loader/RUNPATH into target links;
an environment-only override would not override config.make's assignment.
The target's installed loader paths remain governed by glibc's prefix/rtlddir.
Target CC does not itself request a runtime dependency on the seed. Seed GCC
specs must likewise avoid implicit seed RUNPATH injection. The real build gate
must inspect PT_INTERP, DT_NEEDED and RPATH/RUNPATH of all installed ELF files and
reject seed prefixes; projection alone cannot prove their absence in artifacts.
Shell, make, awk, bison, Python and binutils resolve from the same input, including
shell utilities used for output partitioning. Localedef runs through the newly
built output loader and libraries, with I18NPATH in that output. Partitioning
retains the HostBootstrap recipe's dev/out paths and libc_nonshared linker-script
rewrite. Projection does not establish byte equality of independently built libc.

This factory extends the semantic bootstrap contract: sysroot/usr/lib must also
contain the matching ld-linux-x86-64.so.2, libc.so.6, libc.so linker input,
libc_nonshared.a and every runtime library needed by configure/build helper
programs. crt1.o/crti.o/crtn.o, libc.a and headers remain required. The GCC driver,
its specs and linker scripts must resolve entirely within this admitted prefix;
--sysroot and loader flags alone do not prove that. bin/nm is required alongside
the previously listed binutils. Python must find its admitted standard library,
and bison its admitted skeleton/data files, without host search paths.
BISON_PKGDATADIR and M4 explicitly select share/bison and bin/m4 from that input;
relocation must not leave bison using its compiled-in data or M4 paths. The older
static shape gate does not validate this dynamic bootstrap closure or tool/data
semantics. An isolated compiler trace and actual configure/build probes remain
mandatory before any claim that the seed can build glibc.

The projection fixture binds managed_glibc(tools) into managed_hello(tools, libc),
checking source identities, inputs, headers/sysroot/loader paths, locale handling
and runtime selection. It supplies no real compiler or bootstrap libc. No seed
pin is invented and no source is fetched by this test. Full compilation and
offline execution remain pending on a real seed and a validated Managed backend.

The catalogue also exports managed_hello(toolchain, libc), distinct from its
unchanged default HostBootstrap Hello recipe. recipes/managed_hello.srx and the
default recipe share recipes/hello_source.srx, reusing the existing pinned
Hello 2.12.1 acquisition and produces hello-managed/out/usr/bin/hello. Its
"hello" command selects only libc/out for loader and runtime libraries.

recipes/managed_build.srx supplies a fixed seven-input autotools contract:
compiler, python, runtime, sysroot, tools, libc/dev, libc/out. Every process receives
PATH from compiler/usr/bin, tools/usr/bin and python/usr/bin,
explicit CC/AR/RANLIB, SHELL and CONFIG_SHELL, with a make command-line SHELL
override. Compiler flags select intrinsic headers, Linux UAPI, libc headers and
crt; linker flags select libc/out and its loader/RUNPATH. This is a projection
contract, not a usable toolchain claim. In particular, -B libc/dev/usr/lib alone
does not constrain GCC's default library search or rewrite absolute paths in a
libc linker script. The seed driver must resolve its internals/libgcc from its
own prefix, and the supplied libc linker inputs must reference admitted paths.
Compiler tracing in the isolated executor must prove these properties. No host
shell alias is supplied by this helper; source scripts requiring a hardcoded
interpreter still need explicit upstream-specific handling if encountered.

The local projection test reuses the public main.srx factory export declaration and checks
its source pin, input ordering, compiler/header/crt/loader paths, shell/PATH and
runtime closure. It does not compile or run Hello. A real admitted seed, explicit
Managed execution configuration and successful managed_glibc execution remain
prerequisites for the full seed -> glibc -> Hello build.

Load recipes as a module namespace and bind the supplied references once:

    inputs { recipes = "modules:recipes"; integrations = "modules:integrations"; }
    // tools is an author-selected Toolchain; libc is a RecipeRef.
    // runtime_tools is a separate static shell/pager OutputRef; none is implicit.
    outputs {
        zlib: std::RecipeRef<std::Recipe> = std::recipe_ref(fn() -> std::Recipe {
            recipes::zlib::managed_zlib(tools, libc)
        });
        git: std::RecipeRef<std::Recipe> = std::recipe_ref(fn() -> std::Recipe {
            recipes::git::managed_git(tools, libc, zlib, runtime_tools)
        });
        nginx: std::RecipeRef<std::Recipe> = std::recipe_ref(fn() -> std::Recipe {
            recipes::nginx::managed_nginx(tools, libc)
        });
        shell: std::Shell = std::Shell { pkgs = []; services = [
            integrations::git::git_service(git, "[user]\nname = Example\n"),
            integrations::nginx::nginx_service(nginx,
                "events {}\nhttp { server { listen 8080; location / { root /tmp/www; } } }\n")
        ]; };
    }

The example assumes /tmp/www content is separately provisioned in the session.
It does not create that directory, expose a host directory, or open a listener
merely by projection. The service config remains private and is supplied by the
existing typed File argument. Without content this nginx example returns 404.

managed_git(toolchain, libc, zlib, runtime_tools) produces out/usr/bin/git, with private static
sh and cat validated and copied from runtime_tools into out/usr/libexec/git-minimal. It builds the upstream git
binary target, not the complete installation. Local builtins/configuration are
the intended first proof. Curl/HTTPS, expat, OpenSSL, Perl, Python, Tcl/Tk,
gettext, iconv and gitweb are disabled. Remote transports, helper scripts,
templates, hooks needing additional tools, interactive editor and documentation
are not supplied. The copied shell and pager are private runtime files; the
compiler output is not part of git's runtime closure. Building scripts uses the
seed shell, while the compiled SHELL_PATH points to the installed private shell.
Git v2.55.0's Makefile expects SHELL_PATH_CQ to include the C string quotes; its
compiler flag adds shell single quotes only. The recipe keeps those C quotes
while separately setting SHELL_PATH to the seed for build-time scripts.

managed_nginx(toolchain, libc) produces out/usr/bin/nginx. HTTP core/static files
remain available; PCRE/regular-expression rewrite (including the return directive),
gzip, HTTP basic auth/libcrypt, cache and TLS are not enabled. No docs, sample
configuration, mime table, dynamic module or web content is installed. Logging
uses stderr/stdout; transient PID/lock/body paths use session /tmp. No host
account, privileged port or persistent state location is created by the recipe.

managed_zlib(toolchain, libc) builds zlib 1.3.2 with explicit shell/compiler,
archiver and ranlib. The only make target is libz.so.1.3.2; upstream also builds
the static archive as a prerequisite but it is not installed. The factory
produces dev/usr/include/{zlib.h,zconf.h}, dev/usr/lib/libz.so and
out/usr/lib/{libz.so.1,libz.so.1.3.2}. These library names contain regular copies
of the same shared ELF with SONAME libz.so.1; no symlink or linker script crosses
outputs. There is no command, fake entry, pkg-config file, docs or example
executable. Consumers must select the same libc runtime explicitly, as Git
already does. zlib's runtime RUNPATH names that libc output; its compiler seed
is only a build input. Upstream configure and SONAME/link rules were inspected,
but ELF contents, ABI and runtime closure still require the build/transfer gate.

Explicit input contract (native Linux x86_64, glibc loader ABI)

recipes/toolchain.srx exports Toolchain, also reexported by main.srx. Its required
compiler, python, runtime, sysroot and tools fields are OutputRef<Recipe>, supplied
explicitly by the author. select_inputs fixes those five slots at indices 0..4.
This initial layout supports the inventoried native GNU GCC 16 x86_64 seed only:
  compiler: usr/bin/{cc,gcc}; usr/lib/gcc/x86_64-pc-linux-gnu/16 contains
    include/, cc1, collect2, CRT helpers, libgcc.a and libgcc_eh.a.
  python: usr/bin/python3 and sibling usr/lib/python3.14 with its extension modules.
  runtime: usr/lib contains the selected additional tool runtime libraries.
  sysroot: usr/include supplies bootstrap libc and Linux UAPI; usr/lib contains
    bootstrap crt, libc linker inputs/runtime and ld-linux-x86-64.so.2.
  tools: usr/bin supplies sh, make, GNU binutils, awk, bison, m4 and utilities;
    usr/share/bison retains skeletons/data in the same output as its executable.
GCC_EXEC_PREFIX explicitly selects the compiler's private helper directory;
COMPILER_PATH lists it and tools/usr/bin. No global bootstrap LD_LIBRARY_PATH is
injected into target configure probes. Each tool's normalized interpreter and
RUNPATH must resolve through these declared outputs; original distro paths fail
the seed audit. Merely placing usr/... files in outputs does not establish this.
Python isolated prefix lookup, GCC specs and absolute linker scripts still need
normalization and functional probes. No version/layout auto-detection is promised.

libc must provide dev/usr/include and dev/usr/lib (crt objects and linker inputs),
and out/usr/lib with ld-linux-x86-64.so.2 and its matching runtime libraries.
zlib must provide dev/usr/include/zlib.h and zconf.h, dev/usr/lib linker inputs,
and out/usr/lib/libz.so.1 plus its SONAME aliases. Its ABI must match the selected
libc. The existing glibc recipe has the intended output layout; its own build
still uses the compatibility host profile and is not a reconstructed bootstrap.

Hello/nginx/zlib select compiler/python/runtime/sysroot/tools at 0..4 and
libc/dev, libc/out at 5,6. Git additionally selects zlib/dev,out at 7,8 and a
separate runtime_tools OutputRef at 9. runtime_tools must provide bin/sh and
bin/cat as static executable ELF64 x86_64 regular files. It is not the seed's
dynamic tools output. Before copying either helper, Git invokes declared Python
from input1 to validate both files: bounded headers/program segments, executable
file-backed entry, no PT_INTERP, DT_NEEDED, SONAME, RPATH/RUNPATH or audit/filter
loader directives. Static PIE with relocation-only PT_DYNAMIC is accepted.
Installed private helpers retain those checked bytes; no bootstrap runtime
library is copied into Git or added to its runtime command. This establishes
only ELF shape, not shell/pager semantics or a successful Git build. No actual
runtime_tools provider is supplied by the catalogue.
Git's build scripts still select tools/usr/bin/sh and have their upstream shell
shebangs rewritten before make. This does not replace executor isolation.

Seed admission contract, before a real build

The author supplies five OutputRefs whose admitted outputs contain the layout above;
none of these factories manufactures that reference from an ambient compiler.
A reviewed binary seed admission must record the complete artifact digest,
platform/ABI, provenance, source/build history when available, and every tool
runtime dependency. Check the separate Git static sh/cat provider, execute compiler probes with
host /usr unavailable, and trace cc -> assembler/linker/internals plus header and
library resolution. A projection-only marker file cannot satisfy these checks.
The next runner must reject absent tools and undeclared reads, then build zlib
and nginx before attempting Git. Source bootstrap of GCC/binutils remains a
separate required proof; importing a seed does not establish it.

Executor audit: Copy/Move use the native file walker and Extract uses the native
archive reader. HostBootstrap retains host inventory, mounts and PATH defaults.
Managed preparation does not inventory /usr or synthesize a host-toolchain pin;
its cleared environment starts with an empty PATH. Normal realization requires
the explicit Managed configuration described above. The compatibility execute_build
API still rejects Managed with UnsupportedProfile; callers must use the dedicated
Managed route rather than interpreting this rejection as a missing backend.
Built inputs are verified against their own Action/Receipt provenance, without
requiring producer worker/toolchain identities to equal the consumer's. Imported
inputs are admitted through a pinned ResultManifest and its artifact closure,
with explicit output-key mappings and no fictitious producer Receipt. These input
contracts do not certify the behavior or runtime/data closure of imported tools.
No executor fallback or fake seed is supplied here.

Imported seed admission contract

The obsolete recipes/seed.srx extraction-only, single-out factory has been removed.
The seed is now represented by Recipe.imported = Some(ImportedResult { root,
manifest, entries }), with compiler/python/runtime/sysroot/tools entries selecting
explicit manifest keys. Each output name must match its ResultOutput; there is no
renaming or fictitious Built receipt. The author supplies an already admitted,
pinned result and explicit Store. These factories never scan host tools or infer
an imported root from a directory. Bundle/manifest admission and normalization
remain distinct operations, neither performed by recipe projection.

Run the pure projection/shape tests with the explicit candidate runner:
  python3 scripts/test-candidate.py --core /ABS/syrox --candidate-bin /ABS/srx -- --test seed
The ignored imported-seed shape gate takes SYROX_SEED_RESULT_ROOT,
SYROX_SEED_MANIFEST_SHA256 and absolute SYROX_SEED_STORE. It opens the retained
result, verifies the five selected outputs and audits bounded ELF/data layout.
The dynamic tool closure must use authenticated output prefixes, not /lib64 or
host /usr. Static-worker admission is a separate contract. This gate does not
execute tools or establish ABI/symbol compatibility, dlopen closure or semantics.
No normalized seed is currently admitted. The local regular-byte materialization
recorded below still retains distro ELF paths and is not a passing seed fixture.
Existing default hello/glibc source recipes remain HostBootstrap.

The upstream tool requirements additionally explain why a small LLVM-only kit
cannot close the glibc build: GNU GCC/binutils, GNU awk, bison and Python are
required beyond shell/make. Primary reference consulted for this dependency
inventory (not a version lock):
https://sourceware.org/glibc/manual/latest/html_node/Tools-for-Compilation.html
Python's standard library and bison's data/skeletons must also be within the seed;
isolated probes must establish their lookup paths. Their presence/semantics are
not established by the ELF shape gate. Optional documentation/testing tools and
any version minimum must be checked against the selected glibc source before
claiming a complete glibc toolchain; this factory performs no such claim.

Functional seed gate (separate from shape inspection)

The test-only tests/fixtures/seed-probe.srx factory consumes the selected seed's
five outputs as declared build inputs. It compiles C using explicit bootstrap headers,
crt search, libgcc archive and sysroot, then executes the result directly.
This exercises PT_INTERP/RUNPATH resolution just as configure runs conftest;
invoking the loader explicitly would bypass that check. Volatile 128-bit division/remainder exercise libgcc code generation.
It next invokes bison with share/bison/skeletons/yacc.c and BISON_PKGDATADIR,
compiles the generated parser and runs it through the explicit seed loader. This extends the seed contract with
bin/m4, selected explicitly via M4; bison's data and M4 dependencies must be
present. Finally Python -I imports encodings/json/pathlib, checks their file
paths stay under the seed prefix, and roundtrips structured data. A frozen module
without the required file provenance does not satisfy this initial gate.

Only after all commands exit zero does the program write out/probe.ok. Compiled
probe binaries and generated parser files stay in Work. A per-attempt comment
changes the authenticated C input, and the gate requires Built rather than a
cached/shared witness. These tests do not export another catalogue package.
The pure projection test never executes a compiler and cannot establish success
of any functional probe.

Runtime output acceptance (opt-in, no new build claim)

The existing retained-glibc layout gate and Hello bundle-transfer gate now inspect
all ELF files in glibc dev/out and Hello out. ELF64 x86_64 PT_INTERP must select
the produced glibc/out loader; both DT_RPATH and DT_RUNPATH may contain only its
absolute usr/lib directory. Empty, host, seed, relative and $ORIGIN entries are
rejected by this initial strict gate. Each DT_NEEDED must be a basename supplied
by an ELF file in glibc/out/usr/lib. Filter/auxiliary/audit loader dependency tags
are rejected. CRT relocatable objects are accepted without runtime metadata.
The existing dev/out layout and libc_nonshared linker-script checks remain.

Explicit bootstrap inventory (no admission)
------------------------------------------
`scripts/bootstrap-inventory.py` inventories exact caller-selected package archives;
it does not discover a host cache, extract members into a filesystem, install,
relocate, publish, create a Receipt, or certify a seed. It accepts an input JSON:

  {"version":1,
   "helper":{"path":"/absolute/zstd","sha256":"<64 lowercase hex>"},
   "archives":[{"path":"/absolute/package.tar.zst",
     "sha256":"<64 lowercase hex>","distribution_claim":"unverified origin claim",
     "selected":[{"member":"usr/bin/gcc","role":"compiler"}]}]}

Run with explicit --manifest, --scratch-directory (existing absolute directory),
and --output (must not exist). Input paths must be absolute regular files without
final-component symlinks. The helper and archives are streamed into private pinned
snapshots: SHA256, size and stable source metadata are checked before those exact
bytes are used. Helper version and digest are recorded. The dynamic dependencies
of the inventory helper are not pinned; this is a host inventory tool, not a
managed executor or a reproducible extraction/admission proof.

The helper is invoked by its pinned absolute snapshot, with empty PATH, bounded
stdout/stderr and a 120-second deadline per invocation. Expanded tar bytes spool to
a temporary file, never a whole-archive memory buffer. Before Python tarfile sees
the stream, 512-byte framing is checked: PAX/GNU extension payloads <=64KiB each,
<=1MiB together; sparse files are rejected. Regular selected member digests are
computed in 64KiB chunks (all regular members are hashed during inventory). Files
are never executed. ELF64 little-endian metadata is now inspected by the bounded
parser described below; loader resolution and executable closure remain unverified.

Bounds: input manifest 1MiB; at most 64 archives; compressed archive 128MiB and
expanded archive 512MiB; individual regular member 128MiB; at most 65536 physical
headers per archive and 65536 logical members across the inventory; paths 255 ASCII
characters/depth64; selection link chains 64; at most 128 roles, 128MiB selected per
role and 512MiB selected in total. These inventory limits do not change Syrox's
source acquisition limits. Traversal, duplicate normalized paths, special members,
special permission bits, oversized metadata and trailing nonzero tar bytes fail.
Absolute/escaping links are recorded as unsafe metadata, not followed. Selecting
one, a link cycle or a member beneath a non-directory path fails. Safe relative
aliases resolve only to regular members in that same archive.

Output is deterministic compact sorted JSON with a final newline. It records
archive/member hashes, sizes, selected roles and link chains, with admitted=false,
runtime_closure_verified=false and signature_verified=false. A distro claim is
caller text; a neighbouring signature file is not verification. No normalization
identity or fake build provenance is generated.

The action/prefix is exactly the admission domain documented above, fixed before
rewriting. Source paths are opened through directory descriptors without symlinks;
bytes, modes, path sets, and source pins are checked while copying to a new anchored

ELF policy inspects every selected ELF64 little-endian x86_64 file, including
Python extensions and regularized aliases. It preserves kind, NEEDED, SONAME and
executable-entry shape, refuses unsupported loader directives, sets PT_INTERP only
where one existed, and assigns direct-dependency RUNPATH directories. Providers
must be selected regular ELF shared objects; ambiguous candidates or an earlier
non-ELF file shadowing the selected provider are errors. Names alone do not prove
runtime closure. The independent seed auditor and real probes remain necessary
for symbol versions, ABI, dlopen, NSS/locale, compiler helper discovery and actual
execution. These checks never silently remove tkinter, binutils, Perl scripts or
other members to make the selection appear complete.

Shebang rewriting is deliberately limited to the observed sh (optional single
"-" argument), Python forms including exact env python/python3, and the observed
exact env perl form. Perl maps only to declared tools/usr/bin/perl; it must be an
executable ELF with its required loader, never a host PATH fallback. The
remaining script body and mode are unchanged. Linux passes a single optional
shebang argument, rather than performing shell word splitting; the rewritten
complete line is conservatively limited to 127 bytes, including its newline.
Primary parsing reference: https://raw.githubusercontent.com/torvalds/linux/master/fs/binfmt_script.c
Unsupported interpreters or argument forms are refused; this is not a general
script-language translator. Files without any execute bit are data: their shebang
text is preserved byte-for-byte. This matters for six mode0444 Perl module/helper
files containing relative #!perl or #!./perl lines; the kernel cannot execute
those files. The same relative line on an executable file remains a refusal.
Perl module discovery and execution through an explicit interpreter still require
the functional probe; metadata classification does not prove their behavior.

The concrete libc.so/libm.so GNU linker scripts are recognized, their sysroot
inputs must exist, and their bytes are preserved. Absolute /usr/lib entries in
these scripts are not automatically a host dependency: GNU ld documents sysroot
handling when the script itself is within the sysroot. The relevant compiler
probe must still pass its explicit --sysroot and verify resulting ELF/searches.
Reference: https://sourceware.org/binutils/docs/ld.html (INPUT and --sysroot).
Unknown linker-script profiles are refused rather than rewritten speculatively.
Python _sysconfigdata is preserved as configuration metadata; /usr strings alone
do not establish an external lookup. Expansion/discovery is covered by the
separate Python/GCC/Bison functional probes, not by this byte-preparation report.
Reference: https://docs.python.org/3.14/library/sysconfig.html
No GCC specs are synthesized and no global text substitution is performed.
